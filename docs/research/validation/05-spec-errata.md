## C. Safety design (Spec §4.4, §7; Report 05)

| # | Claim | Verdict | Correction | Severity |
|---|---|---|---|---|
| C1 | Spec §4.4: a 300–400 ms arm window "closes the tool-cancellation race documented in Research Report 02 §4" | **QUESTIONABLE** | It narrows, not closes, the race. `toolCallCancellation` depends on server-side VAD detecting speech start plus WS RTT — report 05 itself notes cloud round-trip and recommends on-device VAD "<30 ms". A 400 ms window is not guaranteed to cover a server VAD decision (and the *default* server `silenceDurationMs` is ~800 ms for turn end; interruption is faster but still not bounded at 400 ms). Fix: (a) run local keyword spotting ("stop/ruko/thamba/cancel") on-device and treat it as the primary cancel for destructive actions; (b) make the arm window a hard floor of ≥500 ms for Tier 3–4; (c) re-validate the target element at the end of the window (TOCTOU: the UI can change in 400 ms). | HIGH |
| C2 | Spec §4.4: pending actions expire after 5 s; demo relies on spoken confirmation | **QUESTIONABLE** (UX risk for the target audience) | 5 s is aggressive for motor-impaired/elderly users with slow speech, and the spec never defines when the timer starts (gate arm vs end of the model's prompt) or what happens if the user starts speaking at 4.9 s. Fix: default 8–10 s, pause/restart timer while user speech is detected, state that the timer starts after the prompt's `turnComplete`, and announce imminent timeout ("still waiting…"). | HIGH |
| C3 | Spec §4.4 Tier 4: "exact read-back phrase plus a mandatory 3-second lock… 'About to confirm payment of ₹500 — say Confirm ₹500'" | **QUESTIONABLE** (safety architecture) | Three problems: (1) **echo self-confirmation** — the model's own read-back can leak through the mic/AEC and be heard as the user's confirmation; require a local no-overlap rule (accept confirmation only when speaker RMS/echo gate is clear *and* after server TTS ends). (2) LLM phrase-matching is unreliable across "₹500" / "paanch sau" / "५००" / partial repeats; use `input_audio_transcription` plus local numeric normalization and exact amount equality, not model judgment. (3) With the fallback model (blocking tools) the read-back timing changes; re-verify. Also handle "Confirm" spoken by a bystander/TV (report 05 flags this `[SPECULATION]`). | HIGH |
| C4 | Spec §4.4: barge-in target <150 ms; hotkey target <20 ms | **QUESTIONABLE** (unverified and inconsistent) | Report 05 claims <120 ms and <15 ms; the spec says <150/<20 without measurement protocol. The Carbon handler→queue-clear→banner path is plausibly single-digit ms, but the voice path includes VAD + WS; and the "hardware action" being halted is async at WindowServer. Fix: define measurement points, instrument both paths, and reconcile the two documents. Also add: on kill, release any synthetically held modifiers (not just mouse-up) to prevent stuck modifier states. | HIGH |

## F. Missing components before implementation

### Must fix before build (the spec has no answer yet)

1. **Wake / activation UX.** There is no definition of how a session starts: always-on mic, wake phrase ("Clicky"), menu-bar toggle, or push-to-talk. Consequences: continuous audio-token cost (≈₹0.43/min of audio in), privacy, and false intent triggers. Add: explicit session start/stop (hotkey or menu bar), a "Clicky" wake gate enforced in the system instruction *plus* local VAD, a visible listening indicator, and idle auto-end (e.g., 90 s silence).
2. **Error handling & reconnect state machine.** Define: `setupComplete` timeout, WS close-code handling, exponential backoff, pre-emptive reconnect on `goAway`, resumption-failure fallback to a fresh session (losing context) and how the UI says so, ephemeral-token refresh before `expireTime`, and what happens to a queued tool call when the socket drops mid-action.
3. **Bundle/run path (TCC + entitlements).** `make-app.sh` contract (Info.plist with `LSUIElement`, usage descriptions), signing order, entitlement set, and a runtime permission watchdog (`AXIsProcessTrusted()`/`CGPreflightScreenCaptureAccess()`/mic authorization polled; spoken recovery + deep links). Also: AppleScript/automation prompts are **per target app** — they will fire during the demo; pre-grant them in the wizard.
4. **Stale-target / TOCTOU protection.** AXHotCache entries are unverified after notifications; notifications miss value/text changes. Before any hardware action, re-resolve the element (role/subrole/title/window) and abort (fail-closed) if it changed; handle "element destroyed between arm and execute"; cap cache rebuild cost (B3).
5. **Confirmation subsystem spec.** Timer start/stop semantics (C2), echo gate + no-overlap rule (C3), local transcript/amount verification, barge-in behavior *during* the confirmation prompt, queue visualization, and what cancels what (new intent vs "stop" vs timeout).
6. **Runaway/loop protection.** Per-turn action budget, duplicate `toolCall` id handling, action rate limiting, repeated-failure circuit breaker, and a cost/action cap that escalates to the kill switch.
7. **Audio device lifecycle.** Handle `AVAudioEngineConfigurationChange` (AirPods/output switch), re-negotiate formats after device change (B9), voice-processing failure fallback (software echo gate), and mic-permission-denied/revoked recovery.
8. **Prompt-injection hardening** per C5 (intent ledger, egress classification, URL allowlist, `enable_prompt_injection_detection`, `safety_decision` handling).
9. **Logging & telemetry.** Wire the latency meter to real segments (defined measurement points), structured redacted logs, crash reporting, and a decision on the audit DB (PII, retention, purge).
10. **Secret handling.** Keychain read/write for `GEMINI_API_KEY`, doctor validation, and no key in logs/args/env dumps.
11. **macOS test matrix.** Current OS (macOS 26 SDK on this machine) + Sequoia 15 on the actual demo laptop; re-verify screen-recording prompt cadence, restart flow, and SCK APIs there (B17).
